# Tomota 严格写作状态机

正式章节只走这一条状态链：

```text
故事圣经 → 章节场景卡 → 设计审查 → 正文
→ 逻辑审查/返工 → 人物对白审查/返工 → 伏笔与承接审查/返工
→ 无提示冷审/返工 → Canon 证据提取 → approved
```

每个审查结论必须有正文或设计证据。问题记录必须同时包含位置、原文、分类、违反规则和修复要求。`evidence` 为空、检查项缺失、存在开放问题或缺少任一审查门时，系统拒绝批准。

## Codex 驱动接口

```powershell
tomota workflow start --book-id demo --chapters 1,2 --max-revisions 5
tomota workflow next --run-id workflow-xxxxxxxxxxxx
tomota workflow submit --run-id workflow-xxxxxxxxxxxx --action-id action-xxxxxxxxxxxxxxxx --file D:\artifact.json
tomota workflow status --run-id workflow-xxxxxxxxxxxx
```

`next` 只生成当前阶段所需的紧凑任务包，并显示阶段、问题数和返工轮次。状态写入 SQLite 和书籍的 `workflow/<run-id>/state.json`，中断后可继续。任一章五轮返工后仍失败，整条队列停在 `blocked`，后续章节不会启动。

## 约束的编译与章节质量交接

Tomota 不把全部约束当作一串同级提示词。完整规则库仍然保留，但运行时只把当前阶段适用规则编译成带 `rule_id`、触发条件、执行步骤和验收条件的记录，并在章节设计里通过 `constraint_application` 映射到具体场景。优先级固定为：硬性质量/发布规则与 Canon → 章节事实和契约 → 本书覆盖 → 作者版本 → 通用 Skill。被上位规则压制的文风规则必须留有公开冲突记录，不能悄悄执行。

每章设计还必须形成两份可审计交接：

- `reader_experience_contract`：本章继承的读者期待、本章实际回报、情绪与信息曲线、不可缺少的局面变化、章末义务和正文验收条件。
- `continuity_handoff`：上一章最终正文的真实尾段、已接受 Canon、原计划与实际落点差异、本章入口/出口状态以及下一章第一拍。

正文阶段读取上一章真实最终尾段，不用摘要代替实际承接。人物对白审查同时扫描此前全部已批准章节，注入的是压缩后的全书开场、章末、句段和重复短语指纹，不是整本旧正文。高置信度的开场骨架或描写反应链重复会退回 `revise_voice` 做完整修订；人物名、世界术语和必要事实不按禁词处理。

用户确认过的返工会保存有上限的前后修改对和统计变化，作为后续相似场景的低优先级写作证据；它不能覆盖 Canon、人物知识边界或章节契约。

## 读后反馈与全书长期规范

读后反馈有“证据定向修订”和“全文审查并全部重修”两种执行范围。全文模式下，用户锁定的已生成章节是操作指令，不属于评估器的质量裁量；评估器必须读取范围内每章全文、逐章引用原文证据并为每章给出重写计划。Canon 只约束必须保留的事实、因果和人物知识边界，不能作为拒绝或缩小用户重写范围的理由。

每项确认的问题必须同时归纳成不依赖单句的全书质量规则，并覆盖本轮全部修改项。规则先作为候选公开展示；用户确认返工后，以可追踪的反馈来源写入 `book_style_overrides`，再由 `CompiledWritingPolicy` 编译进后续章节设计、正文和审查任务。硬性格式、安全、Canon、发布规则和章节事实始终优先于这些风格规则。若全文评估漏章、证据不是正文原句、修改项没有对应长期规则，系统必须拒绝进入返工。

## 存储与清理

每章工作区只保留当前稿与上一稿。更早的工作稿、完整提示词和临时报告移动到 `books/<book-id>/.trash`；默认保留七天。手动清理永远先预览：

```powershell
tomota cleanup --book-id demo
tomota cleanup --book-id demo --apply
```

单书回收区上限为 100 MB；超限时从最旧回收内容开始清理。清理器只能删除 `.trash` 内文件，不能选择最终稿、章纲、Canon、人物/伏笔账本、审查报告或发布记录。云端内容不属于清理范围。

上面的七天回收规则只适用于日常版本整理。“删除章节/卷”或“只保留书名与封面，推倒重建”是另一条显式确认的永久清理链：成功后不保留正文、章纲、Canon、Prompt、审查、反馈、任务、发布预览、旧 `.trash` 或 Studio 恢复包。全书重建只保留作品编号、标题、`assets/` 封面和作者版本绑定；平台上已经提交或发布的内容不在本地清理范围内。执行中先使用仓库根目录下的临时隔离区保证文件与数据库一起回滚，成功后临时区也会删除，因此不能作为恢复入口。

## 番茄边界

浏览器会话只记录 `logged_in/auth_required` 和页面可见作品信息，不记录 Cookie、Token、密码、验证码或二维码。默认范围仅包括作品、章节草稿、审核状态、排期和运营数据。实名、合同、收益、银行卡、税务和安全设置全部阻止；作品或公开章节删除永不自动执行。

发布桥接分三道边界：严格审查证据通过、明确批次确认、浏览器写入与逐章提交的操作时确认。遇到登录失效、验证码、风控、页面结构变化、网络不确定或重复章节时停止并重新读取状态，不盲目重试。

### 提交检查点与恢复

Studio 新提交采用 schema 3。点击最终发布前，先将本章 `submission_started=true`、正文指纹、远端身份和提交前目录 ID 集合写入回执；文件先写临时文件并同步到磁盘，再原子替换。写入失败时不能点击。每章核验成功后立即保存回执，不等整批结束。后续未发送章节保留 `not_attempted`，已经可能发送的章节保留 `uncertain`。

正常完成和断线恢复共用核验器：完整目录中的作品 ID、章号、标题、章节 ID、已发布/审核中状态，以及重新打开编辑页后回读的完整正文必须同时匹配。标题相同、字数相同、缓存记录和成功提示均不能单独证明提交成功。恢复只读取原始导出正文，不重新导出覆盖；本地回写再校验正文指纹和完整正文核验凭证。AI 使用声明仍固定选择“否”，不改变操作确认机制。

目录读取遍历可识别的分页和原生分卷选择器；自定义分卷选择器必须能够明确切换“全部分卷”。页数不推进、总数变化、缺页、重复 ID/章号、未知分页或分卷结构均停止，完整读取成功前不替换目录缓存。真实平台改版可能需要适配，不以部分结果继续提交。

Studio 另存批次启动标记。已启动却缺失回执、回执损坏或旧回执缺失必要证据时，不自动视作未执行，也不允许直接重发或废弃。应先核验平台；无法证明时保留待核验状态。新建章节缺失提交前 ID 基线时同样不自动认定成功。这些保护降低重复提交风险，并不声称能跨本地与平台实现原子事务。

补充约束：

- AI 声明只读目标控件的实时 `checked`、`aria-checked` 或对应自定义单选状态。固定的 `value=no`、旁边的“已选”文字和其他控件的选中状态均不构成证据。
- 替换章节还要求持久保存本次最终点击后的官方成功提示，绑定作品、远端章节、章号和正文指纹。提交前残留的成功提示会阻止点击。缺失该凭证时，即使编辑器读回新草稿也保持待核验；这不是读者端正式版本核验，也不声称已适配平台业务响应协议。
- 浏览器导航、同步、预检、提交、恢复与账号关闭等操作共用 SQLite 原子领取的操作锁。同一工作流内部可重入，其他请求/Studio 实例收到 `browser_busy`，不会操作同一页面；只自动清理由已确认退出进程留下的锁。释放操作锁不会清除提交检查点。
- `fanqie check --batch <id> --json` 只校验正文，不导出文件。重复导出复用且不覆盖相同快照；快照内容不同或开始执行后快照丢失时拒绝重建。Studio 将启动标记同时持久化到数据库与 `.started.json`。
- 回执消费以整份规范化回执的哈希去重，章节、批次、数据库事件与消费记录在同一 SQLite 事务内提交。发布回写的权威审计记录在数据库 `events`，不另做无法与数据库原子提交的 JSONL 双写；同一回执重试不重复生成数据库事件。

离线发布回归：在 `studio` 运行 `npm run test:publishing`。其中真实 DOM 测试启动独立无头浏览器并拦截全部请求，不复用账号或访问真实平台。可用 `TOMOTA_TEST_BROWSER` 指定浏览器；缺少浏览器时 DOM 项会明确跳过，不能据此声称页面验证通过。
